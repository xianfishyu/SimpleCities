    V4 道路长度读取分配优化¶

    日期：2026-10-04；关联 GitHub #25；修复前实现检查点 9bcb972c。 证据：.scratch/v4-edge-length-20261004/；此前完整分配调用栈见 v4-allocation-stacks-20261003/after/。

    最新完整分配跟踪中，RoadEdge.get_Length() 的采样字节权重约为 276 MB。源码每次读取通过 Zip/Skip/Sum 重新枚举不可变点列，调用者包括路面准备、网格预检、查询索引及位置解析。本轮先建立精确分配回归，再在道路构造时按原先从左到右的顺序计算一次长度，保存在对象内。点列仍先复制、再只读封装；不使用延迟初始化、锁或共享缓存。

    数值、分配与存储取舍¶

    4,096 组 Length + PointAt(0.5) 读取在旧实现分配 1,507,328 B，零分配断言失败；新实现为 0 B，通过同一断言。该计数不包含构造、测试输出或断言本身，不代表整个编辑操作零分配。

    新增测试以原 getter 表达式作为数值参照，逐位比较空点列、单点、重复点、平移折线、闭环、821 点直接模型输入及非有限值；非法直接模型输入只用于保持既有 getter 语义，不表示它们通过生产准入。另验证原始数组修改不会影响道路、公开点列不可写、record 副本及各个参数位置保持稳定。与既有延长道路、Codec 和历史回归一起 47/47 通过。

    缓存也有成本：同一 x64 运行时，持有 4,096 条三点道路的构造分配从 622,592 B 变为 655,360 B，即每条道路多 8 B。约 10K 条道路对象对应约 80 KB 的额外标量存储；没有按历史条目或整个进程外推精确总量。存档没有增加字段；RoadEditHistory.EstimatedBytes 原本是领域载荷估算而非堆实测，公式及所有产品预算保持不变。

    独立 Release Core 探针从正常载荷取得快照，预热后测量 RoadPresentation.Prepare，五套有序表面指纹全部相同：

    10K 表面准备少分配约 1.84 MB（约 8.7%）。另一阶段的真实 Godot 网格准备从上一轮已验证的 26,815,920 B 基线降至本轮 24,975,920 B；固定网格 SHA256 仍为 ED5D5DC330625ACD11C7E5BC025F8145FF6BE5FFA355556F536BE34DDCEFC013，143,064 顶点/163,704 索引/44,248 片。不能把这两个阶段的数字当作整个操作或保留堆大小。

    无跟踪 Release 对照¶

    顺序前→后→后→前。两版均优化 ExportRelease，25 米/10K、1600×900 Vulkan Forward+、Dummy 音频、默认 GC、相同帧时间探针、无 VSync/帧率上限。每组预热 5 秒，四个基础窗口各 1 秒，5 轮共 60 次操作，另有 20 次取消及 1 秒空闲；采样期间没有构建、其他测试或基准。

    V4 GC 配置语义核对¶

    日期：2026-10-03；关联测量：生产源码 b5c74bd 的 GC 模式复核。 范围：官方文档与指定运行时提交的静态源码核对；没有运行构建、测试或游戏，没有修改 GC 默认设置。

    DOTNET_GCHeapCount=8 会在本次运行时对应的源码中关闭 DATAS；它不是“保留 DATAS、最多使用 8 个堆”的配置。 初始化请求 8 个服务器 GC 堆，实际数量还会受到可用处理器等限制。显式再设 DOTNET_GCDynamicAdaptationMode=1 也不会取消这一覆盖规则。S3

    版本与证据边界¶

    当前导出包报告的 CoreCLR ProductVersion 为：

    10,0,1226,42308 @Commit: 95017c711e6afc1085133d440e42b4bd78155701

    该完整提交属于微软的 dotnet/dotnet VMR，并非 dotnet/runtime 仓库中的提交。官方提交接口能定位它；该提交的 src/source-manifest.json 将 runtime 映射到 https://github.com/dotnet/runtime 的 4271d88e0aebf3d04f188f1334c2220d80555ef6。S1 下文源码证据均固定到这一 VMR 提交的 src/runtime/，没有用 main 或另一个发行标签替代。

    这是按导出包提供的 @Commit 标识完成的源码匹配，未重新构建或对二进制做反汇编验证。Microsoft Learn 页面是本次读取到的现行公开说明，源码引用则是上述固定提交；以下分别标明公开文档、实现与测量推论。

    官方文档与默认值¶

    配置 公开文档的含义 对应提交的默认值与解释
    DOTNET_gcServer / System.GC.Server 0 / false 为工作站 GC；1 / true 为服务器 GC。运行时默认工作站 GC。D1 ServerGC=false。S3
    DOTNET_GCHeapCount / System.GC.HeapCount 限制服务器 GC 创建的堆数，仅用于服务器 GC。D2 HeapCount=0 表示未请求具体堆数，不表示创建零个堆。未指定时先按进程可用 CPU 等计算容量；DATAS 启用后从一个活动堆开始。S3S5
    DOTNET_GCDynamicAdaptationMode / System.GC.DynamicAdaptationMode 1 启用、0 禁用 DATAS；从 .NET 9 开始默认启用。D3 默认 1，但非零 HeapCount 会把内部生效模式覆盖为 0。DATAS 的动态堆数实现受 USE_REGIONS && MULTIPLE_HEAPS 编译条件约束，不能由此推断工作站 GC 也会动态增加堆数。S3S6

    “默认值”指运行时的缺省配置；宿主和应用配置可以提供其他值，不能仅因某个环境变量未设置就断言实际模式。当前 CoreCLR 的 gcServer 布尔查询直接读取启动后确定的 GC 类型。D1

    官方 DATAS 说明同时包含三项行为：根据长期存活数据控制分配预算、根据吞吐量调整实际预算、按需要增加或减少堆数。因此，禁用 DATAS 的影响超出了 GC 线程/堆数量本身。D4

    GCHeapCount=8 是固定请求，还是动态上限¶

    该提交的初始化逻辑先读取模式，再执行以下覆盖：S4

    dynamic_adaptation_mode = (int)GCConfig::GetGCDynamicAdaptationMode();
if (GCConfig::GetHeapCount() != 0)
{
    dynamic_adaptation_mode = 0;
}

    据此可直接得到以下实现结论：

    • HeapCount 未设置或为 0，且模式为 1：保留 DATAS；启动时活动堆数设为 1，随后可自适应改变。S4
    • HeapCount=8：走非 DATAS 路径；初始化按请求的 8 个堆计算，不再通过 DATAS 自适应改变堆数。即使模式同时指定为 1，仍被覆盖成 0。S4
    • “固定 8 堆”有适用条件：源码会把请求数量截断到进程可用 CPU 数、实现支持的最大堆数、适用的 GC 亲和性集合数量，并在初始化时处理其他内存约束。故不能承诺任意机器、任意附加配置下都恰好 8 个；这里也不把堆数解释为整个游戏的 CPU 核心或总线程上限。S4

    此处必须同时保留两层含义：官方公开文档称 HeapCount 为“限制堆数”，而当前实现用非零值选择了关闭 DATAS 后的指定堆数路径。仅把它描述为“DATAS 的 8 堆上限”会漏掉关键行为。D2

    保留 DATAS 时能否另外限制堆数¶

    源码层面存在独立的 DOTNET_GCMaxHeapCount / System.GC.MaxHeapCount，本次未确认其公开支持承诺。 该提交的配置表将其默认值设为 0，描述为 “Specifies the max number of server GC heaps to adjust to”；初始化将容量截断为 min(nhp, max_nhp_from_config) 后写入 n_max_heaps。关闭 DATAS 的条件只检查 HeapCount，不检查 MaxHeapCount。S3

    因此，在未设置非零 HeapCount、DATAS 模式为 1 的前提下，GCMaxHeapCount=8 在该版本实现中表达“保留 DATAS、将可用堆容量限制在至多 8 个”，并仍从一个活动堆开始。这是静态源码结论，本次未执行该配置。S4S8

    本次有界核对了 Microsoft Learn 的 GC 配置页和 DATAS 概念页，并以 GCMaxHeapCount 查询 Learn 官方搜索接口；前两页未列出此项，搜索返回 count=0。故不能仅凭配置键出现在源码中，把它标为有正式公开文档保证的生产调优接口，也不能把它的支持状态断言为“不受支持”。关于“保留 DATAS 并限制 GC 并行度”的公开受支持配置，本次结论仍为未确认；没有扩展到 CPU 亲和性调优。D1D5

    环境变量的十六进制规则¶

    官方规则是：GC 数值配置在 runtimeconfig.json 中按十进制填写；环境变量按十六进制填写，可以带或不带 0x。对应提交的 GCToEEInterface::GetIntConfigValue 也以 u16_strtoui64(out, &end, 16) 解析环境配置字符串。D1S7

    期望数值 环境变量字符串 JSON 数值
    8 8 或 0x8 8
    12 C 或 0xC 12
    16 10 或 0x10 16
    32 20 或 0x20 32

    所以本次的 GCHeapCount=8 没有进制歧义；环境字符串 16 则表示十进制 22，不能拿来表达 16 个堆。gcServer 与 DATAS 的 0 / 1 在这两种进制下数值相同。GC 配置在初始化时读取；修改已运行进程之外的环境变量不会让该进程重新初始化 GC。D1

    对本次测量能作出的推论¶

    已有短测记录中，普通服务器组观测到 1 → 3 → 5 → 8 → 13 → 20 → 31 个堆，显式组在跟踪范围内均为 8 个。这与上述 DATAS/非 DATAS 初始化路径相符；仅凭观测序列本身不能代替配置源码证明，也不能将 31 当作机器或运行时的固定上限。S4S8

    在同一台 9950X3D / RTX 5080 的 25 米、10K 规范道路边短测中，工作站、普通服务器、显式 8 堆三组的响应 P95 为 94.826 / 67.890 / 61.278 ms，超预算帧为 155 / 87 / 12，采到的工作集峰值为 737.9 / 892.7 / 1436.1 MiB。这些是已有项目测量，非官方文档给出的性能保证，也未在本次研究中复测。

    这组对照同时改变了堆数量策略与 DATAS 开关，不能把变化单独归因于“GC 并行度降为 8”。 源码还显示，DATAS 开启且 GCConserveMemory 配置为默认 0 时，内部节省内存级别会设为 5；关闭 DATAS 时不会执行这一默认提升。因此更高工作集与配置变化存在相容解释，但本次不能量化其中各机制的贡献，也不据单机短测推荐生产默认配置。S3D4

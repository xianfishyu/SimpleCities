    V4 主线程表现准备拆分与剩余长尾¶

    日期：2026-09-30 对应工单：GitHub #25；本次是局部瓶颈修复与开发环境复验，#25 保持未完成。 修复前：074957e；原始序列、调用栈、失败尝试与验证记录：.scratch/v4-25-20260930/。

    2026-10-02 后续：本文当时保留的普通 Load 同步预检问题已由加载专项复验处理；本文的 2026-09-30 测量和范围记录仍作为历史证据保留。

    问题与证据¶

    240 边夹具重新运行后出现 40.864 ms 帧长尾，一次 redo 的主线程表现预检耗时 37.5733 ms。相同引擎下的 25 米 10K 场景，64 次改造/删除/历史操作的主线程预检 P95 为 89.4635 ms、最大 103.3064 ms，编辑窗口最大帧 105.666 ms。

    Godot 4.7 Mono（5b4e0cb0f）、Vulkan Forward+、RTX 5080、1600×900、VSync 关闭、max_fps=0。对照场景预热 3 秒，每个静止/相机/悬停/相机加悬停窗口 3 秒，8 轮各 8 次编辑/历史操作，另保留两次预热操作。两轮均由相同 target-probe.gd 驱动普通槽位加载及真实输入，均通过 92 项检查。完整帧序列与操作阶段时间保存在 target-before/ 和 target-after/，未去除操作帧。

    在单独诊断进程上用 dotnet-trace 10.0.745401 的 dotnet-sampled-thread-time,gc-collect 采集 10 秒。可解析的 target-trace3/cpu.nettrace 显示：主线程 V4RoadDisplay.Prepare 栈累计采样区间约 6518 ms，其中构造显示索引约 2907 ms、SurfacePreflight.Validate 约 1743 ms；索引构造内部的 SpatialQueryIndex 约 2262 ms。这些是有包含关系的采样墙钟区间，不能相加，也不是所有线程的 CPU 占比。它们与逐操作计时共同确认主线程承担了大量纯数据工作。

    首次采集误连 godot_console.exe 启动器，没有取得 trace；第二次进程退出截断 trace，topN 报错；第三次连接实际 godot.exe 并在游戏退出前停止采集，转换及读取成功。前两次不作为调用栈证据。也没有根据采样中的 finalizer/等待线程占比把所有长尾归因为 GC。

    实现边界与同环境对照¶

    V4RoadDisplay.PrepareGeometry 负责坐标转换、严格表面检查、数组和拾取索引准备；编辑及手动显示恢复在既有 worker 上完成它。返回的一次性 PreparedGeometry 只持有托管数据，尚未创建 ArrayMesh。主线程 Upload 创建并验证引擎资源，随后沿用原有可提交性检查、原子引用发布、正确首绘确认和旧资源保留流程。

    取消检查覆盖路面片、端接表、按边分组及空间索引的输入枚举、桶构建、最终转换。单个数组复制和单边排序仍不可中断；本次没有设定 #26 的取消时限产品预算。普通 Load 的整套 preflight 仍同步执行，本次没有改写联合加载协议。

    新增 geometryMs 独立记录后台显示数据准备，surfaceMs 继续表示纯道路表面生成，preflightMs 现在记录主线程上传及引擎检查。不能把移走的时间当作被消除的工作量。

    最终四档与补充场景¶

    tests/godot/v4_target_performance.gd 复用基线的槽位加载、真实输入、首绘计时和原始帧序列记录。最终每场景预热 3 秒，四种连续渲染窗口各 5 秒；目标场景另运行 8 轮三格改造/删除及历史、8 轮建造及历史和 20 次 Esc。200 米满铺先删除三个格段创造合法建造空间，测量后通过历史恢复；补充 320 条折线单列，测单格改造/删除，不冒充满铺建造。

    最终表及逐阶段分位数由 summary.json 的 final-* 项生成；完整原始序列在各 final-* 目录。输入开始边界为 C# 输入处理器接受建造/拖选松开或历史快捷键，结束为对应 token 首次 frame_post_draw；同时保留外部注入到观察完成的时间。它们是注入输入的开发环境样本，不代替正式发行包的人机延迟测试。

    100/100 次 Esc 被接受，worker 退出最大 4.4185 ms、工具恢复最大 4.5362 ms。此场景在发起历史操作后立即按 Esc，未覆盖每个最深算法阶段，也未出现提交竞态；竞态语义由异步正确性契约另行验证。这些样本不冻结 #26 的预算。

    正确性、工具与数据导出¶

    • 完整自动化：Core 363/363、Application 968/968；Debug/ExportRelease 构建 0 警告、0 错误；最终主 solution Roslyn（含分析器）0 诊断，三个相关 GDScript LSP 文件均零诊断。新性能脚本已从 QA 导出资源排除，导出契约通过。
    • 表现预检/恢复扩展至 99 项，新增 worker 准备后上传、预取消不产出候选、一次性上传检查；异步取消和加载失败/成功隔离契约继续覆盖旧状态与资源所有权。
    • 编辑器临时继承场景运行 100 米 10K：32 项资源检查、35 项容量/交互检查、10 次实际输入操作通过。截图确认灰色背景网格、道路和高亮；DAP stdout 取得通过结果、stderr 为空，增量编辑器错误为空。
    • 五套容量回归保留 159 项、46 次成功操作，包含保存/重载、几何与身份恢复、水位、拒绝原子性及临时槽删除。

    容量回归曾两次在 Variant 终结器崩溃。独立工作树运行未修改的 074957e 也在 Variant(String) → DescribeEdges → GetRoadState 崩溃，证明不是本次后台几何准备新引入的问题。该测试只需要几何摘要，却反复导出全部边、路口、incidence 和 turn 的 native Variant 树。

    容量比较现改用 GetRoadContentFingerprint：v4-core-content-v1 的 SHA-256 包含地图格长、全部节点身份/位置，以及边身份、端点、类型和 binary64 折点，排除单独断言的 token 与分配水位。覆盖强于旧 Vector2/JSON 边摘要，所有比较和状态断言保留；新旧摘要格式不可直接比较。该措施避免容量验证的大型原生状态导出，并未修复或确证 Godot/CLR 原生崩溃根因，GetRoadState() 大规模导出风险仍存在。

    尚未完成的验收¶

    1. 仍有超过 6.9444 ms 的帧，包含无编辑窗口和补充折线场景；不能仅凭 P95 关闭 #25。需对这些残留窗口逐帧关联 GC/调度/驱动等事件，再进行同环境对照。
    2. 后台表面与显示数据准备仍消耗时间和临时内存；目前只是移出主线程，下一步应按实测分配/阶段成本分别优化。
    3. 普通加载的同步 CPU preflight 尚未拆分；应在联合提交、坏载荷拒绝和失败恢复契约保护下独立处理。
    4. 本次没有正式导出 Release 的持续前台验收，也未覆盖所有地图边缘/长链分布。五秒窗口用于本轮可复现复验，不能宣称稳定 144 FPS。

    5. 26 的累计/单笔历史预算、裁剪与取消恢复预算仍待产品确认；#22 正式切换、#23 旧路径清理不在本轮完成范围。远端工单状态未修改。¶

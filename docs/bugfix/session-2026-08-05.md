## SESSION-BUG-01：旧折线提交路径把原生曲线当作端点弦线处理

> 候选系统：`road-graph`

### 症状

图中已经存在通过 `SubmitPath()` 保存的 Bezier、圆弧或其他原生曲线时，再通过旧的 `SubmitPolyline()` / `AddRoad()` 添加道路，交叉口和完整覆盖判断可能与实际显示曲线不一致：真实曲线上的交叉点不会拆分既有边，或者系统会在曲线弦线上的错误位置尝试拆分。

### 根因分析

`GraphEdge` 的权威几何保存在 `GeometrySegments`，但 `GetFullPath()` 只返回 `[NodeA.Position, ..._points, NodeB.Position]`。对于只有一个原生曲线段的边，`_points` 为空，因此返回的是两个端点组成的直线弦。

旧折线路径的 `ResolveIntersections()`（`Scripts/Road/RoadGraph.cs:388-434`）、`IsPathCovered()` / `CollectExistingSubSegments()`（`Scripts/Road/RoadGraph.cs:563-613`）和 `FindEdgesContainingInteriorPoint()`（`Scripts/Road/RoadGraph.cs:698-718`）都依赖这条折线路径；而 `SubmitPath()` 的原生路径规划才使用 `GeometrySegments` 和 `RoadGeometryIntersectionQuery`。空间索引能够把曲线边选为候选，但候选之后的几何计算已经退化为弦线。

例如，Bezier 端点为 `(0,0)`、`(16,0)`，控制点为 `(0,16)`、`(16,16)` 时，曲线中点为约 `(8,12)`，而 `GetFullPath()` 的弦线中点为 `(8,0)`。新建 `y=8` 的水平线时，真实曲线会相交但弦线不会；新建 `x=8` 的竖线时，旧路径会在 `(8,0)` 收集错误交点，而 `SplitEdgeAtPosition()` 再用权威曲线查找该位置会失败，最终留下没有真实连接节点的交叉道路。

### 修复方案

未执行修复。需要统一旧折线 API 与原生几何查询的交叉、覆盖和拆分语义，或明确禁止两套 API 在同一 `RoadGraph` 中混用，并补充“原生曲线后提交折线”的回归场景。

### 影响范围

影响已经加载或由公共 `SubmitPath()` 创建原生曲线后的 `SubmitPolyline()`、`AddRoad()`、交叉拆分和重复覆盖判断。只使用折线 API 的旧路径，以及只使用原生 API 的路径规划不属于该混合场景。

### 验证状态

- 静态根因已由 `GraphEdge.GetFullPath()`、`RoadGraph.ResolveIntersections()` 和 `RoadGraph.PathSubmission` 的数据流确认；当前代码和现有测试分别覆盖折线路径及原生路径，未覆盖两者混用。
- 本轮 MCP 已确认项目运行连接正常，但无法通过 GDScript 直接构造非 Node 的 `RoadGraph` 并调用该混合 API；因此没有把运行时混合场景写成已验证通过或已修复。
- 当前仅记录发现，未修改 `Scripts/Road/GraphEdge.cs`、`Scripts/Road/RoadGraph.cs` 或其他道路代码。

## SESSION-BUG-02：最近节点/边查询未在入口校验非法位置和半径

> 候选系统：`road-graph`

### 症状

公开的 `FindClosestEdge()` 和 `FindClosestNode()` 接收到负半径或 `NaN` 半径时静默返回 `null`；接收到包含 `NaN` 的位置时不会在查询入口给出参数错误，而会在空间索引遍历到几何引用后从 `RoadGeometrySegment.EnsureClosestPointArguments()` 抛出 `ArgumentException`。同一 `RoadGraph` 的 `FindEdgeIDsNear()` 对这些输入会在入口明确拒绝。

### 根因分析

`FindEdgeIDsNear()` 在 `RoadGraph.cs:210-227` 先检查 `position.IsFinite()`、半径有限性和非负性；但 `FindClosestEdge()`（`RoadGraph.cs:178-208`）及 `FindClosestNode()` 转发到的 `FindClosestIndexedNode()`（`RoadGraph.cs:248-275`）没有同等校验，直接把参数传给 `UniformGrid.QueryRadius()`。负半径使查询桶的最小/最大坐标反转，循环不执行并返回空结果；`NaN` 位置继续进入 `EdgeGeometryRef.IntersectsCircle()`，最终由几何层而不是公开查询 API 报错。这样同一类空间查询的异常契约不一致，也把调用方错误暴露成依赖候选实体和实现细节的行为。

### 修复方案

未执行修复。需要让两个最近查询在进入 `UniformGrid.QueryRadius()` 前复用与 `FindEdgeIDsNear()` 一致的位置和半径校验，并保持正常有限正半径查询的边界包含语义不变。

### 影响范围

影响所有直接调用 `FindClosestEdge()` / `FindClosestNode()` 的道路工具、拆路悬停和外部数据层调用在收到非法输入时的失败方式。正常的有限坐标和非负半径查询不属于该根因；道路拓扑、存档格式和空间索引数据本身不受此发现影响。

### 验证状态

- 隔离 xUnit 夹具覆盖负半径、`NaN` 半径和 `NaN` 位置：`FindEdgeIDsNear()` 均抛出参数异常；两个 `FindClosest*()` 对前两类返回 `null`，对 `NaN` 位置均从 `EdgeGeometryRef.IntersectsCircle()` 路径抛出 `Point must contain finite coordinates`。
- `dotnet test tests/SimpleCities.RoadGraph.Tests/SimpleCities.RoadGraph.Tests.csproj --no-restore --filter FullyQualifiedName~InvestigationInvalidSpatialQueryTests`：3/3 通过；输出仅包含既有 `NU1900` NuGet 漏洞源警告。
- 当前仅记录发现，未修改 `Scripts/Road/RoadGraph.cs`、`Scripts/Road/SpatialIndex.cs` 或其他生产代码；隔离夹具已删除。

## SESSION-BUG-06：键盘相机移动速度随帧率变化

> 候选系统：`camera`

### 症状

相同的实际输入时长下，键盘移动距离会随 `_Process` 调用次数变化。低帧率时移动较短，高帧率时移动较长；缩放平滑也会表现出不同的响应速度。

### 根因分析

`MainCamera._Process(double delta)` 接收了 `delta`，但没有使用它。`KeyPosUpdate()` 每次调用都把固定大小的 `moveInput` 增量加到 `nextPos`，并使用固定的 `Position.Lerp(nextPos, 0.1f)` 系数。移动积分和平滑插值都以“每帧”而不是“每秒”计算，因此帧率改变时结果不保持时间一致。

### 修复方案

未执行修复。需要将移动增量和插值系数改为基于 `delta` 的时间积分/时间一致平滑，并重新验证不同帧率下相同输入时长的位移。

### 影响范围

影响 `MainCamera` 的 WASD 镜头移动和缩放响应，以及依赖相机位置的地图观察体验。存档坐标格式和道路图数据不受此记录影响。

### 验证状态

- MCP 冻结运行时中，使用相同一秒模拟时长分别手动执行 30 次和 60 次 `_Process`，并传入对应 `delta`（`1/30` 与 `1/60`）；相机 X 位移分别为 `133.6345` 和 `318.8511`，确认结果依赖调用频率。
- 当前仅记录发现，未修改 `Scripts/MainCamera.cs`，因此没有修复验证结果。

## SESSION-BUG-07：中键拖动重复累计初始位移

> 候选系统：`camera`

### 症状

中键拖动相机时，拖动位移可能逐帧放大，表现为过冲、加速或松手前镜头持续偏移。

### 根因分析

按下中键时，`_Input()` 只把当前世界坐标保存到 `mousePos`。中键保持按下期间，`MousePosUpdate()` 每帧计算 `mousePos - GetGlobalMousePosition()`，这个值是“按下点到当前点”的总位移，却被每帧再次累加到 `Position`。代码没有更新上一帧鼠标位置，也没有使用鼠标事件提供的增量；同时相机自身移动会改变 `GetGlobalMousePosition()`，使重复累计进一步放大。

### 修复方案

未执行修复。需要改为每帧消费相邻鼠标采样的增量，或使用一次拖动基准配合稳定的相机/鼠标坐标变换，并为中键按下、移动、释放分别验证。

### 影响范围

影响 `MainCamera` 的中键平移操作。键盘移动、缩放和存档数据不属于该根因。

### 验证状态

- 静态代码路径已确认：`_Input()` 在 `Scripts/MainCamera.cs:90-92` 只记录一次 `mousePos`，`MousePosUpdate()` 在 `Scripts/MainCamera.cs:56-64` 每帧重复使用同一基准计算位移。
- 本轮 MCP 输入接口没有提供可控的绝对鼠标位置与中键持续状态组合，因此未完成真实中键拖动回放；该条保持“发现、未修复、运行时场景待补充验证”。

## SESSION-BUG-08：相机存档恢复未遵守 min/max zoom 边界

> 候选系统：`camera`

### 症状

### 修复方案

未执行修复。需要在存档准备或提交阶段统一验证/钳制 zoom 与当前有效 `minScale`、`maxScale` 的关系，并明确处理非法导出配置，随后验证越界存档不会改变相机到边界以外的目标值。

### 影响范围

影响加载外部或损坏存档后的相机缩放目标和地图可视范围。正常由鼠标滚轮产生的存档值已经经过现有边界钳制；相机位置、道路图数据和存档 JSON 字段格式不属于该根因。

### 验证状态

## SESSION-BUG-09：`RoadRenderer.SetGraph` 绑定已有道路图时不会初始化渲染缓存

> 候选系统：`road-rendering`

### 症状

向已经包含道路边的 `RoadGraph` 绑定一个新的 `RoadRenderer`，渲染器的 `_edgePoints` 仍为空，静态道路 mesh 也不会建立。此后只有新边触发 `EdgeAdded`，或图主动触发 `GraphCleared`，才会开始填充显示缓存。

### 根因分析

`RoadRenderer.SetGraph`（`RoadRenderer.cs:81-93`）只取消旧图事件并订阅新图事件，没有清空旧缓存、遍历新图已有的 `GetAllEdges()`，也没有调用 `RebuildStaticBatches()`。已有边的 `EdgeAdded` 事件发生在绑定前，无法补发；当前 `RoadSystem._Ready()` 恰好先创建空图再绑定，因此正常首帧路径不会暴露这个问题，但重绑定或依赖注入预填充图时会出现空渲染。

### 修复方案

本次只记录问题，未实施修复。绑定新图时应使缓存与新图当前状态同步，并清理旧图的边缓存；具体修复尚未执行。

### 影响范围

影响所有在图已有边之后调用 `SetGraph` 的道路渲染器实例，包括预填充存档图、运行时切换图实例和测试夹具。正常 `RoadSystem._Ready()` 的空图初始化以及之后通过 `EdgeAdded`、`GraphCleared` 驱动的路径不受此代码路径影响。

### 验证状态

## SESSION-BUG-14：原生曲线内部吸附回退到远端端点

> 候选系统：`tool-input`

### 症状

指针位于原生 Bezier 曲线内部、且仍在道路交互半径内时，如果网格吸附后的查询点没有命中道路，开始铺路会把起点放到曲线端点，而不是指针附近的曲线位置。用户会看到新铺路会话从远离光标的端点开始。

最小场景使用端点 `(0,0)`、`(400,0)`，控制点 `(0,400)`、`(400,400)` 的单段 Bezier。指针位于 `(251,351)` 时，曲线中点 `(200,300)` 距指针约 `72.1`，小于配置的 `80` 交互半径；实际回退却把预览起点设置为 `(400,0)`，该点距指针约 `381.3`。

### 根因分析

`RoadBuilder.BeginPlace()` 先把指针吸附到网格，再用吸附点执行 `FindClosestEdge()`。当该查询失败时，`FindNearestRoadPoint()` 用原生几何查询确认指针附近存在边，但随后调用 `GraphEdge.GetFullPath()`，只遍历端点和旧折线 waypoint。

单段原生曲线没有 `_points`，所以 `GetFullPath()` 只返回两个端点。方法没有在 `GeometrySegments` 上求最近曲线位置，最终选择了距离两个端点较近的 `(400,0)`，即使真实曲线内部就在光标交互半径内。

### 修复方案

未执行修复。需要让回退吸附使用权威 `GeometrySegments` 的最近位置，或明确规定曲线只能吸附端点并在交互层拒绝内部命中；两种方案都需要补充曲线内部、端点和折线 waypoint 的输入回归。

### 影响范围

影响 `RoadBuilder.BeginPlace()` 在原生 Bezier、圆弧、Clothoid 或其他非折线几何附近的开始铺路行为，尤其是网格吸附点落在道路交互半径之外而原始指针仍命中道路的场景。普通折线的端点 / waypoint 回退、道路删除和图拓扑提交不属于本条根因。

### 验证状态

- `godot.exe --headless --path . --log-file .godot/qa-road-curve-snap-investigation.log --script tests/godot/road_curve_snap_investigation.gd`：退出码 0；真实 `MapTest` 运行时加载 Bezier 夹具后，`BeginPlace(Vector2(251,351))` 输出 `fallback=(400,0) edgeID=3`，并读到预览起点 `(400,0)`、渲染边数 `1`。
- 同一运行输出 `PASS road curve snap investigation`，临时夹具和手工存档槽已清理；`ConstructionDock: ToolManager.Instance is missing` 是该独立场景启动时的既有降级警告，不是本条失败信号。
- 当前仅记录发现，未修改 `Scripts/Road/RoadBuilder.cs` 或任何道路实现。

## SESSION-BUG-16：仅大小写不同的系统文件名会相互覆盖

> 候选系统：`save-system`

### 症状

在 Windows 文件系统上，两个 `ISaveable` 分别声明 `SaveFileName = "Economy"` 与 `SaveFileName = "economy"` 时，保存操作返回 2 个系统文件已写入，但槽位内实际只有一个 `economy.json`。加载后两个系统都会得到后写入系统的状态，而不是各自的状态。

### 根因分析

`SaveSlotStore.GetDataFileName()` 保留调用者的大小写，`Save()` 也使用大小写敏感的列表记录两个 payload；因此 manifest 会合法地列出 `Economy.json` 和 `economy.json`。但 Windows 文件系统不区分这两个名称，第二次 `File.WriteAllText()` 覆盖第一次写入。加载路径的 `HashSet<string>` 和 `Dictionary<string, ISaveable>` 同样按 `StringComparer.Ordinal` 区分大小写，最终让两个系统从同一个物理 JSON 文件恢复。

### 修复方案

未执行修复。系统文件名唯一性和 manifest 文件表应采用与目标文件系统一致的大小写规则，或在保存前拒绝大小写不敏感的冲突名称。

### 影响范围

影响 Windows 编辑器和 Windows 导出包中未来同时注册大小写不同系统名称的存档 profile。当前 V2 profile 只有 `road_network`，不会触发此冲突；问题会在增加多个可保存系统时出现。

### 验证状态

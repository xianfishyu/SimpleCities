    测试基础设施 Bug 修复记录¶

    日期：2026-10-03 影响文件：tests/SimpleCities.RoadGraph.Tests/RoadRendererLoadPrepareTests.cs 关联事项：GitHub #25 验证时发现的既有测试调度问题

    BUG-1：线程池复用使后台准备测试偶发误报¶

    症状¶

    完整测试运行中，PurePreparer_CanRunOnWorkerWithoutRendererAndIsDeterministic 在 Assert.NotEqual(callerThread, workerThread) 失败，两者均为 42；所属测试集其余 967 项通过。失败发生在比较准备结果之前，不是已经观测到两次准备结果不一致。

    根因分析¶

    测试在 await Task.Run 前记录调用线程号，并假定任务一定由不同物理线程运行。调用方让出线程后，线程池可以复用同一个线程执行排队的委托；Task.Run 没有提供该测试所假定的独立线程前提。

    修复方案¶

    用 Task.Factory.StartNew 的同步委托、TaskCreationOptions.LongRunning 和 TaskScheduler.Default 明确建立独立后台线程，再等待结果。保留原线程身份、全部顶点/索引/表面/来源和确定性断言，没有改为接受同线程，也没有修改生产加载准备器。

    影响范围¶

    只修正这一项测试的运行前提，不改变游戏的任务调度、加载行为或线程池配置。与触发验证的 V4 边界分配优化分别提交。

    验证状态¶

    • 初次失败原始记录：.scratch/test-worker-isolation-20261003/failure.log。
    • dotnet test tests/SimpleCities.RoadGraph.Tests/SimpleCities.RoadGraph.Tests.csproj --no-restore --filter FullyQualifiedName~RoadRendererLoadPrepareTests --verbosity minimal：28/28；随后使用 --no-build --no-restore 连续四轮，均 28/28。
    • 修复后所属完整 Application 测试集 968/968，未删除或跳过断言，见 application-tests.log。
    • dotnet build SimpleCities.sln --no-restore：0 警告/错误；Roslyn 重建五项目后编译器/分析器诊断为空。仅属测试调度修改，按 Tier 1 验证。

    BUG-2：游戏先退出使 CLR 跟踪缺少正常结束标记¶

    症状¶

    V4 双变量实验中，四份采集器退出码为 0 的原始跟踪都在解析时抛出 Read past end of stream。块审计确认最后顶层块完整，但缺少 NullReference 结束标记与最终序列点，取消及末尾空闲阶段无法当作完整无丢失证据。

    根因分析¶

    游戏在测量结束后直接清理并退出，外部采集器仍按更长的固定时长运行。目标退出使流复制提前结束；该版本 dotnet-trace 的路径会跳过主动 session.Stop()，并仍打印完成。采集进程成功退出不保证流正常收尾。旧文件只能进行明确受限的前缀恢复，不能补造缺失事件。

    修复方案¶

    • tests/godot/v4_target_performance.gd 增加可选 collector 握手。全部窗口关闭后，原子发布唯一 token/PID 和测量末端时间；等待匹配的停止确认再执行原有清理/退出。等待帧不计入采样，并检查等待期间道路状态保持不变。
    • Scripts/QA/capture-v4-clr.ps1 使用现有 DiagnosticsClient API，在目标仍存活时 StopAsync，等待流排空并关闭文件，检查结束字节后原子发布确认。
    • read-v4-clr-events.ps1、inspect-v4-clr.py 和 validate-v4-clr.py 分别执行真实解码、块/最终序列点检查和端到端证据校验。旧文件不会因退出码为 0 而通过。
    • 默认不启用握手，生产 C#、GC 配置、场景及原有测量窗口不变。

    影响范围¶

    属于测试基础设施的采集生命周期，不是道路长帧的生产修复。既有采样和原始流保留；此前安全前缀结论不改写为完整跟踪结论。

    验证状态¶

    • .scratch/v4-trace-finalization-20261003/handshake-checks.json：默认路径 49 项检查通过；缺确认、错 token、错 PID、失败确认四组均仅在预期的 collector_acknowledged 失败，全部清理临时槽。
    • release-ready/clr-validation.json：真实 Release 73 项检查、12 次测量操作通过；原生前台 95/0。原始 49,530 字节跟踪直接解码 284 个事件，丢失计数 0；结束标记和最后 SPBlock 均存在，全部 8 窗口的 5,459 帧位于完整覆盖内。
    • Stop 在测量末端后 26 ms 请求，停止及排空耗时 114 ms；停止前与排空后目标都仍存活。取消和 settle 窗口均被覆盖，无需追加字节或截取前缀。
    • 六项校验器检查通过，包含旧残缺原文件、错误确认身份、提前停止、目标已退出和事件丢失的否定检查。
    • 120 次操作的扩展运行同样得到正常结束标记和覆盖测量末端的最终序列点，解码 2,772 个事件、丢失计数 0；但全程失焦，因此性能验收失败并保留原始记录。
    • dotnet build SimpleCities.sln --no-restore --verbosity minimal：0 警告/错误；新 Release 两个游戏程序集均优化。GDScript 诊断为空，编辑器另记录 3 条既有 LSP 客户端重复打开文件错误；独立 CLI 验证不代替编辑器输入/DAP 门。

    BUG-3：补充折线夹具跳过建造和对应历史流程¶

    症状与根因¶

    v4_target_performance.gd 的 build_window 对 polylines 直接返回，验收窗口下限也为其减少一项。此前补充折线报告仅覆盖改造、删除、历史和取消，没有建造覆盖；增加 settle 窗口也不能证明建造执行过。200 米满铺需要先腾出建造空间，但这一前提不适用于同格长的补充折线。

    修复方案与范围¶

    补充折线执行与其他夹具相同的建造、撤销、重做、撤销复原流程；腾出空间、边界内缩和恢复原路仅用于 200 米 target 满铺。Release 验收单独要求存在有帧的 buildAndHistory 窗口。只改变 QA 覆盖，不修改生产道路逻辑或放宽性能门。

    验证状态¶

    • 新 v4_target_build_runtime_contract.gd 调用同一个 build_window，覆盖五套夹具、每套两轮；验证完整操作顺序、准确一次窗口、内容及 ID 复原、临时槽删除，91 项通过。测试覆盖的实际序列包含补充折线建造。
    • godot_console --path . --script res://tests/godot/v4_target_build_runtime_contract.gd 的完整输出与结构化结果位于 .scratch/v4-target-build-20261005/；明确不收集帧率或延迟样本。
    • 两个 GDScript 经任务专用编辑器的真实 LSP 诊断为空。编辑器/DAP 功能验收另见 记录。正式持续性能须在新增覆盖后重跑，功能通过不代表 FPS 达标。

    2026-10-08 校验器收口¶

    summarize-v4-release.py 同步要求补充折线的 buildAndHistory 窗口和每轮 12 次测量操作，支持显式 settle 窗口。五组最终 Release 2388 项、1,805,354 帧通过；对真实报告分别删去建造窗口和建造操作，校验器均在对应门拒绝。原报告未改写，证据见 .scratch/v4-cleanup-20261008/checker-negative-validation.json。

    BUG-4：隔离导出未绑定实际源码副本¶

    症状与根因¶

    2026-10-08 的清理审查发现：新增 ExportProjectPath 可以导出独立物理副本，但 runner 只记录原仓库 source hash；旧副本也可能被标成当前源码的验收结果。副本提供规避编辑器 DLL 共享锁的能力，不自动证明它与记录源一致。

    修复方案与范围¶

    export_source_identity.py 在导出前核对原源码 hash、实际副本逐文件 hash 和输入清单，仅允许明确的 project.godot 编辑器 MCP 插件关闭差异；测量后再次核对实际输入。summarize-v4-release.py 强制验证源/副本 manifest 对应及当前副本 hash。此修复属于验收身份保护，不改变生产道路逻辑、GC 或性能目标。

    验证状态¶

    本轮 278 个实际输入绑定通过，553 文件双副本 manifest 前后核对通过；真实报告替换一个副本源码 hash 后被拒绝。正式矩阵重算通过，原执行 runner 按 hash 归档。审查后的两个物理构建路径完整程序集 hash 分别留存，3553 个方法签名/属性/IL 和全部 C# 源输入一致；未将方法一致性冒称完整文件 hash 相同。详细范围见 最终验收。

    更新后的 runner 实际短流程 71 项通过，前后 278 输入身份均通过；首次准确拒绝编辑器自动序列化造成的 RoadConfig 文本差异，归档并恢复后重跑通过，未放宽只接受准确 hash 的门。

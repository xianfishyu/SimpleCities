# V4 目标规模容量与合法数据集

本报告对应 [#24 容量扩展与四档合法代表性数据集](https://github.com/xianfishyu/SimpleCities/issues/24)，记录 2026-09-13 的公共规划构造、严格存档往返和核心/真实Godot编辑验证。25/50/100 米档各 10,000 条规范道路边、200 米档 9,680 边满铺及独立折线场景均已生成，五份核心测量记录和106项Godot容量断言全部成功。领域计数采用 [CONTEXT](../../CONTEXT.md) 的规范道路边，不以格段、路口或表现三角形代替。

这是容量与正确性证据，不是目标规模 144 FPS 或 100–300 ms 输入响应通过。[#25 帧长尾与达标复验](https://github.com/xianfishyu/SimpleCities/issues/25) 仍需完成真实渲染测量；[#26 历史/取消预算确认及准入](https://github.com/xianfishyu/SimpleCities/issues/26) 的产品预算也没有由此次容量扩展自动确定。正式场景装配不在本报告范围。

## 准入边界

生产资源边界从 512 节点、256 边、2,048 链点、1 MiB 读取载荷，调整为 **32,768 节点、16,384 边、131,072 链点、32 MiB 读取载荷**。schema 6、深度 6、四档固定格长、两轴 ±4000 米、八方向与格心仅对角等规则保持不变，不引入迁移或测试专用放行。

16,384 边为当前 10K 规模和编辑切分提供边数余量；32,768 节点允许每条边独立拥有两个端点；131,072 链点相当于边数上限的八倍，为多段折线提供独立预算。32 MiB 载荷避免约 1.3 MB 的目标数据集被旧 1 MiB 入口拒绝，并继续保持明确字节上限。以上是有界实现预算，不是所有预算极值能同时在每档地图合法实现的承诺，也不是内存保留量或延迟预算。

拓扑验证在已经确认的米字方向下，使用半格整数坐标枚举闭线段上的潜在相交位置；候选仍由原有精确相交/重叠规则验证。所有合法方向的交点都在半格坐标上，因此可缩小两两比较范围而保留端点接触、共线重叠与未节点化交叉的拒绝能力。这个论证不适用于任意方向或未来曲线。Codec 使用有界增长的流读取，继续拒绝未知/重复字段、无效水位、非法地图与超限实体。各边界和坏存档验证的最终测试结果在工程验证部分记录。

## 构造规则

生成器 [RoadCapacityDatasets.cs](../../tests/SimpleCities.RoadCore.Performance/RoadCapacityDatasets.cs) 只调用公开 `PlanBuild` 与 `TryCommit`，不手工伪造载荷或快照。格坐标乘当前格长得到米坐标。核心米字区为 `[-20,20]²` 的 40×40 主格：41 条水平长线、41 条垂直长线、79 条 `y-x=d` 对角线和79条 `x+y=s` 对角线，共 **240 笔正长度建造**。其中 d、s 各取 -39 至 39，并裁剪到主格区域；±40 的零长度极角不提交。

该完整区有 `6×40²+2×40=9,680` 边、`41²+40²=3,281` 结构节点，其中 1,600 个格心路口、1,681 个主格点路口。200 米档此时覆盖整张地图，达到用户确认的满铺规模。

前三档另放置 320 条独立 L 形折线。它们以八列、四十行排列，起点为 `(-40+2列,-40+2行)`，从起点`(x,y)`依次连接`(x+1,y)`、`(x+1,y+1)`。每个 L 由两笔建造合并为一条三点规范道路边，相邻 L 之间保留一格间隔。整个补充区 x≤-25，与米字区 x≥-20 分离；100 米档也位于地图内。最终 **880 笔建造产生10K边**，同时包含密集路口和局部集中排列的 320 条折线。每条折线只有一个转折；高链点、长折线和更多折线占比的压力成本不能由这一夹具外推。

200 米满铺的全部边都是单原子直段，不能在同一满铺快照额外保留多段折线。其补充场景使用二十列、十六行独立 L，起点 `(-20+2列,-20+2行)`，同样沿x正向一格、y正向一格；640 笔建造合并为 320 条折线。它是单独的较低边数场景，不冒充 9,680 边满铺性能。

| 数据集 | 规范道路边 | 结构节点 | 链点 | 可选格段 | 格心路口 | 主格点路口 | 折线边 / 内部链点 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 25 / 50 / 100 m 各自目标 | 10,000 | 3,921 | 20,320 | 10,320 | 1,600 | 1,681 | 320 / 320 |
| 200 m 满铺 | 9,680 | 3,281 | 19,360 | 9,680 | 1,600 | 1,681 | 0 / 0 |
| 200 m 补充折线 | 320 | 640 | 960 | 640 | 0 | 0 | 320 / 320 |

格段统计通过公开 `RoadSpanQuery.Pick` 对每条折线的半格内部采样，并按带来源版本的格段键去重；生成器对表中预期计数逐项断言。折线格段数和规范道路边数分别保留。

## 产物、正确性与复现

每个场景输出 `.road.json` 和 `.measurements.json`，位于 [.scratch/v4-24-qa/datasets](../../.scratch/v4-24-qa/datasets)。原始 stdout 和退出状态对应 `capacity-100.log`、`capacity-25.log`、`capacity-50.log`、`capacity-200.log`，四次运行退出码均为 0。100 米先独立运行，随后按25、50、200米顺序分别启动 Release 控制台进程；200 米进程继续生成补充场景。

```powershell
dotnet run --project tests/SimpleCities.RoadCore.Performance -c Release -- --capacity-datasets .scratch/v4-24-qa/datasets 100
foreach ($capacityCell in @(25,50,200)) {
    dotnet run --project tests/SimpleCities.RoadCore.Performance -c Release --no-build -- --capacity-datasets .scratch/v4-24-qa/datasets $capacityCell
    if ($LASTEXITCODE -ne 0) { throw "Dataset construction failed: $capacityCell" }
}
```

五份数据均通过严格 Codec 读取、新 Network 的 `PlanLoad` 与引用提交、再次写出的字节一致性验证。加载后历史为空。每份加载结果都执行一个格段类型改造，再撤销、重做、撤销；随后执行一个格段删除及同样的历史序列。内容哈希包括格长、节点/边身份、连接、类型和链点，验证撤销与重做确实恢复对应内容；身份水位和变更序列不混入内容恢复判据。删除单格可能使邻接二度点重新规范化，例如10K场景删除后为9,998边；这不意味着多删除了一个可选格段。

## 工程与 Godot 验证

核心 **339/339**、应用 **968/968** 通过。独立边界验证包含32,768节点/16,384边合法快照、满边数下切分整笔拒绝、32,769节点数组提前拒绝、131,072合法锯齿链点往返和131,073点拒绝；载荷测试使用不可seek流，精确32 MiB接受、32 MiB+1在哨兵处拒绝并保持活动状态。32,769节点测试使用null哨兵区分数组准入与后续实体解析，不将其称为合法地图。原有坏存档、字段、八方向、主格点/格心路口、自环、平行边、重叠和取消回归继续通过。

Debug方案、ExportRelease游戏和独立性能控制台Release构建均为零警告、零错误。方案内8个改动C#文件的Roslyn诊断及已信任方案分析器为空；独立工具的`Program.cs`、`RoadCapacityDatasets.cs`不在solution中，CodeLens覆盖仍受限，以独立Release构建和五套实际执行作为适用验证。容量GDScript的LSP诊断为空。

真实运行使用Godot 4.7 stable Mono Debug、Forward+/Vulkan、RTX 5080、1600×900视口，执行[容量运行脚本](../../tests/godot/v4_capacity_runtime_contract.gd)。四档目标与200米补充场景均经严格Codec装入后创建实际ArrayMesh、绘制至Current；随后真实鼠标按下选择一个格段、松开改造，再撤销，接着删除和撤销；每次要求当前表现、token变化和实际拾取类型/区间相符。之后使用正常SaveManager保存，切到另一格长的空图，再从存档加载，确认格长、规范边数、当前表现及空历史恢复。五个调试槽位均已删除。总计 **106/106**，退出码0，结果见[godot-result.json](../../.scratch/v4-24-qa/godot-result.json)。

测试最初选用四分之一格位置；25米档该点位于八向路口表现区域，真实拾取返回路口，尚未选定分支，因此没有格段。最终使用水平格段中点以符合分支选择规则，保留恰好一个格段的断言。删除L的一条腿可能仍剩一条规范边，故以实际选中位置消失、token改变和撤销恢复为判据，不以总边数必然减少作替代。此处修正的是测试假设，未因此修改生产拾取行为。

编辑器另在1064×599嵌入视口加载100米10K数据，真实单格改造后撤销；DAP stdout确认通过、stderr为空，运行前cursor847至停止前858无新增编辑器错误。更早的seq820为LSP客户端重复打开文件的工具记录，不隐去也不计为运行错误。临时场景和脚本已删除，游戏停止，仅保留证据文本。详情见[editor-result.json](../../.scratch/v4-24-qa/editor-result.json)、[editor-dap.json](../../.scratch/v4-24-qa/editor-dap.json)及[最终验证记录](../../.scratch/v4-24-qa/verification.md)。

以上运行是正确性验证，没有性能预热和重复采样设计。编辑器单次改造输入到首绘为 **343.2942 ms**，其中主线程预检 **144.4783 ms**；撤销API到首绘为239.5449 ms。这一观测超过300 ms目标，并暴露主线程同步成本，应在#25中单独测量和处理，不能因106项功能断言通过而宣布响应或144 FPS达标。ExportRelease构建通过也不等于Release渲染实测通过。

容量数据集完成后可直接用于 #25 的真实渲染复验。100K仍不属于当前16,384边准入范围，只有25/50米档在几何上可构造，不通过非法几何或跳过预算补足压力数量。

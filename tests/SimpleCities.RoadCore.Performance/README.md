# V4 历史与取消资源基线

这是仅引用 `SimpleCities.RoadCore` 的独立 .NET 10 控制台，不进入游戏生产装配，不修改 solution。使用公开的建造、道路格段查询、类型改造、历史、快照和取消接口；没有反射或放宽地图/拓扑限制。

从仓库根目录复现：

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project tests/SimpleCities.RoadCore.Performance -c Release -- .scratch/v4-20-qa/history.json
```

关闭分层编译避免测量期间 JIT 生命周期引入非历史对象回收；环境变量仅属于当前进程/子进程。四档格长为 25、50、100、200 米，所有几何都在 ±4000 米地图中。每个格长/场景先预热一次，再独立创建五次 64 笔有效历史，不把种子建图操作计入结果。

## 测量定义

- `EstimatedBytes` 原样读取 `RoadEditHistory`：领域载荷系数估算，实体端点可能重复计数，不是准入预算。
- `MarginalHistoryManagedBytes`：先退出生成路网和计划的独立 `NoInlining` 栈帧，仅持有公开 `Snapshot` 和 `History`。始终强持有**同一个**当前快照及其索引，测量释放历史前后的 `GC.GetTotalMemory(false)` 差。没有用重新加载的不同快照作差，因此当前快照共享实体不会被错误算作可释放历史。这是历史的边际托管存活字节，包含历史管理对象；不是所有历史实体大小之和，更不是操作分配总量。
- 每次读堆之前重复三轮阻塞、压缩全代 GC，每轮都等待终结器再进行第二次 GC，报告三次读数的极差。此次 100 组历史实验前后极差均为 0，四档每种场景五次差值一致。进程级测量仍受运行时全局缓存影响，不主张通用的逐对象精确堆分析。
- 两次读堆之间仅使用 `Stopwatch.GetTimestamp()` 的整数时间戳测量回收时间，不新建存活的计时器对象。预审发现迭代器路径的 `Stopwatch.StartNew()` 会污染第二次读数，修正并重跑后未提交计划差值增加 40 B；历史同步路径的本次差值保持不变。
- `Sharing` 在生成阶段只通过公开 `ChangeSet` 计数实体端点出现次数、引用身份去重后的对象数及与当前快照共享数；测量前丢弃所有统计用对象集合。节点/边以外的几何数组、元数据、集合对象不在该计数里，其空间仍包含于托管堆差值。
- `ProcessWorkingSetBytes` 只作环境背景。它包含 JIT、运行时、原生分配、已提交但尚未归还的 GC 页，不能作为历史独占空间，也不能将前后工作集差叫作“实际历史内存”。
- `OperationMs` 包含本夹具的格段构造/查询、核心 Plan 和 Commit。它不含 Godot 输入、表现准备、主线程预检、上传或首次绘制，不能验收 100–300 ms 或 144 FPS。

## 2026-09-13 结果

以下历史实测对应提交 `8a484cb` 的 V4-20 基线，不随后续代码修改重新解释。#24 已扩展生产容量；旧版本的 256 边限制和第 257 边拒绝记录不代表扩容后的行为。默认工具仍只用 257 条独立道路做轻量旧上限探测，全部接受时输出 `ObservedStatus=Ready`、`EdgeCount=257` 和 `Former256EdgeLimitNoLongerBinding=true`，不递增构造至新上限，也不从 257 条成功推断新容量。扩容规模证据由独立 `--capacity-datasets` 分支输出，复现命令与五套统计见[容量报告](../../docs/performance/v4-24-capacity.md)。

原始环境、每次读数及取消样本保存在 `.scratch/v4-20-qa/history.json`。下表数值在四档、各五次重复中相同：

| 64 笔操作场景 | 历史估算 B | 边际托管存活 B | 最大单笔估算 B |
| --- | ---: | ---: | ---: |
| 64 条相互独立的一格直路建造 | 31,744 | 38,840 | 496 |
| 连续 32 格直路中间一格反复 Street/Highway 改造 | 57,344 | 56,384 | 896 |
| 连续 32 格直路整段反复改造 | 28,672 | 29,800 | 448 |
| 64 条独立一格直路一起反复改造 | 1,060,864 | 774,208 | 16,576 |
| 当时上限 256 条独立一格直路一起反复改造 | 4,206,592 | 3,042,880 | 65,728 |

连续道路的 32 个可选格段规范化后仍可只有一条边，因此它的历史比局部切分一个格段更小。256 边批量场景的 32,768 个变更实体端点对应 16,640 个不同引用对象，其中 256 个仍属于当前快照。估算未去掉这些共享；相反，简单建造的估算小于边际堆，说明固定系数也遗漏对象/集合开销，不能把估算统一视作实测上界。

在该历史基线版本中，第 257 条互不相交直路通过公共 `PlanBuild` 被拒绝，活动边数保持 256，原因为“超过当前道路路网的资源上限”。当时 10K 规范道路边不能经生产准入构造；此报告不通过伪造不合法快照凑数，不把 256 边称为 10K 性能通过。

## 取消与未提交计划释放

取消实验使用 256 条合法独立道路，每次将 256 个格段的类型改造放在独立线程中。线程发出入口信号后约 0.1 ms，调用者向公开 `CancellationToken` 发出取消；记录**调用 Cancel 前的时间戳到工作线程 finally 中的时间戳**。四档各预热一次、采样十次；此次 40/40 为 `OperationCanceledException`，当前快照引用均未改变，延迟范围 0.0219–0.1935 ms。

此入口信号不是规划器内部检查点，不能证明每次取消在相同算法阶段。它也不是 Esc 事件到 UI 恢复时间，不包含工作线程终结后的任务调度、Godot 帧循环和预览清理。样本代码保留 `Ready` / `CompletedBeforeSignal`，更快机器上规划提前完成时不会伪计为取消成功。

公开 `RoadPlan` 没有显式 Dispose，它的域数据由 GC 回收。额外实验强持有同一个活动 Network（含原历史）并丢弃一个已准备但未提交的 256 格段计划，四档各五次得到 206,008 B 边际托管存活空间。清理后的三轮全代 GC 用时每档上界为 13.82、13.56、14.83、15.73 ms；历史实验为 7.8851–16.5960 ms。这些是**强制全进程 GC 的实验成本**，不能叫作计划自身 Dispose 耗时或取消响应延迟，生产也不应为此主动全代 GC。

## 预算建议与适用边界

当前样本最大 64 笔历史约 2.90 MiB 边际堆、4.01 MiB 领域估算；最大单笔估算约 64.2 KiB。可以将累计估算 8 MiB、单笔估算 256 KiB 作为后续监测/压力测试的候选阈值，分别保留约 2 倍/4 倍本次已测值的余量。**本次不将它们写成生产拒绝门**：256 条直路未覆盖 2048 点折线、密集路口的最坏变化，未来解除 256 边限制后必须重新测量；粗估也不是一致的堆上界。单笔超限不建议静默丢弃撤销记录或删除有效编辑，应在完整压力样本明确后再选择提交前显式拒绝或其他产品策略。

纯核心 token 取消可先用 10 ms 作回归警戒线（本次最慢约 0.194 ms），但不能据此冻结 Godot Esc 全链路预算。未提交计划只要求引用不再被保留；自然 GC 的回收时机不能承诺为固定毫秒。

本工具 Release 编译成功并完成上述实测；它没有 Godot 依赖，因此不替代主任务的方案构建、Roslyn 及真实渲染验收。`Program.cs` 未加入 solution，需把这一点明确为 solution 范围 CodeLens 的覆盖限制。
